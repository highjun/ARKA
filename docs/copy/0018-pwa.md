# ADR 0018: 클라이언트는 설치 가능한 PWA다 — 앱 셸만 캐시하고 API는 캐시하지 않는다

## 결정:
- `vite-plugin-pwa`로 manifest와 Service Worker(`app-sw.js`)를 만든다. `display: standalone`, 아이콘 192/512(+maskable).
- **프리캐시는 앱 셸(정적 자산)뿐이다.** `/api/*`는 절대 캐시하지 않는다 — 낡은 파일 목록·내용이 화면에 남는 것이 가장 나쁜 실패다.
- `registerType: 'autoUpdate'` + `skipWaiting` + `clientsClaim` — 새 빌드가 뜨면 SW가 갱신되고 열린 탭이 새 셸로 바뀐다. 그래도 남는 틈(갱신 전 낡은 셸이 새 서버를 치는 순간)은 프로토콜 헤더([ADR 0017](0017-protocol-header.md))와 "다시 불러오기" 띠가 메운다.
- SW 파일명은 `app-sw.js`다. `/sw.js`는 서버가 kill-switch로 차지한다 — 이 호스트명에 예전 PWA가 남긴 Service Worker를 걷어내는 스크립트이고, 그 기기가 언제 다시 올지 몰라 지우지 않는다.
- 개발 서버에서는 SW를 켜지 않는다.

## 기각:
- **PWA 없이 두기** — 프로젝트 정의(§0)가 "PWA 웹앱, 설치 없이 여러 기기"를 전제하고, 폰이 정본 폼팩터다. 홈 화면 설치와 standalone 창이 없으면 브라우저 크롬이 IDE 밀도의 화면을 잡아먹는다.
- API 응답 캐시(오프라인 읽기) — 워크스페이스는 서버 디스크가 원본이고 쓰기가 있다. 오프라인에 읽은 낡은 내용을 다시 쓰면 서버의 새 내용을 덮는다. 오프라인은 지원하지 않는다.
- SW 이름을 `sw.js`로 — kill-switch와 충돌한다. 새 SW가 옛 등록을 대체하긴 하지만 그 순간 kill-switch의 `caches.delete`·`unregister`가 사라져 옛 캐시가 남을 수 있다.
- 수동 갱신(`prompt`) — 사용자가 미루면 낡은 클라이언트가 계속 426을 맞는다.

## 상태:
승인됨. `docs/ADE.md` §0의 PWA 전제를 코드로 옮긴 것이다. [ADR 0015](0015-protocol-version.md)가 전제했던 "PWA가 폰에 캐시된다"가 이제 사실이다.
