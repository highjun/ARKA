## 설명

client 계층 결정이 "정해지지 않았다"고 남겨둔 것들. 셋이 얽혀 있어 함께 답한다.

**① `services/`가 필요한 조건** — `services/`가 `features/filesystem`에만 있고 나머지는
`transport`가 `infra`를 직접 부른다. 계층 규칙이 이를 허용하지만("필요할 때만") **언제 필요한지가
문장으로 없다.**

**② feature마다 인터페이스 유무가 갈린다** — `agent`만 `domain/`에 인터페이스 4개와
`implements` 6건을 갖고 `filesystem`·`git`·`search`·`static`은 0개다.

유력한 설명(미확정): 서버는 `Mock*`이 **0개**이고 테스트가 `mkdtemp`·실제 `git init`으로
**실물을 쓴다.** 대역이 없으니 구현이 하나뿐이고, 구현이 하나면 인터페이스가 통과 계층이 된다.
반면 `agent`는 `ScriptedRunner`↔`AnthropicRunner`로 **진짜 바꿔 낀다.** 이 설명이 맞다면 규칙은
**"바꿔 낄 것이 있으면 `domain/`이 인터페이스를 선언하고, 실물을 그냥 쓰면 자유 함수"**가 된다.

**③ `features/static/`에 `domain/`이 없다** — 도메인 개념이 없어서 안 만들었다. "빈 레이어를
미리 만들지 않는다"에 부합한다. ②의 결론에 흡수될 수 있다.

딸린 결과: 유지하기로 하면 서버 슬라이스의 계약 리뷰 대상이 TS 인터페이스가 아니라
`contracts/`의 zod 스키마 + 라우트 시그니처가 된다는 점을 `CONVENTIONS`에 적어야 한다.
