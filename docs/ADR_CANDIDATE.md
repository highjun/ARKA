# ADR 후보

검토 중 나온 **구조적 결정**(전역적으로 다른 부분에도 영향을 미치는 결정)을 여기 쌓는다.
유닛 하나에서만 끝나는 지적은 여기가 아니라 할 일 태스크(`docs/tasks/`)로 간다.

검토가 끝나면 각 항목은 둘로 변환된다 — `docs/adr/NNNN-*.md`(결정과 기각 이유), 그리고
가능하면 **강제 장치**(`ops/lint/rules/` 또는 CI 검사). 규칙으로 만들 수 없는 것은 ADR만 남긴다.

## 형식

```markdown
### 제목
- **무엇이 걸렸나**: 어디서 어떻게 드러났는가
- **결정할 것**: 한 문장
- **선택지**: A / B / C와 각각의 대가
- **강제할 수 있는가**: 예(어떤 장치) / 아니오(왜)
- **상태**: 열림 / 결정됨 → ADR NNNN
```

---

## 결정됨 — ADR 승격 대기

### 와일드카드 DNS 자리표시 — 새 호스트 이름이 30분 잠금을 만들지 않게

- **무엇이 걸렸나**: PR 미리보기를 확인하려고 데스크톱 브라우저로 `pr-19-arka.sangjun.dev`를
  열었더니 `ERR_NAME_NOT_RESOLVED`. **모바일에서는 열렸고, 반복해서 겪었다.**

  원인은 이렇다. 미리보기는 PR마다 **한 번도 존재한 적 없는 이름**을 만드는데, 그 레코드는
  잡이 시작된 **2분 54초 뒤**에 생긴다(실측: 잡 05:52:20 → DNS 05:55:14). 그 사이에 한 번
  열어 보면 리졸버가 NXDOMAIN을 받고 **`sangjun.dev`의 SOA 최소 TTL인 1800초(30분)** 동안
  그 답을 재사용한다. 레코드가 생겨도 그 기기만 30분 동안 막힌다.

  **"떴나?" 하고 일찍 확인하는 것이 자연스러운 행동인데, 구조가 그 행동을 30분 잠금으로 벌했다.**

- **결정할 것**: 존재하지 않는 이름의 응답을 무엇으로 만들 것인가.

- **선택지**
  - **A. 규율 — 뜬 뒤에만 주소를 연다.** 비용 0. 그러나 **답이 아니다** — 주소가 `pr-<번호>`로
    뻔해 먼저 눌러 볼 수 있고, 실제로 내가(에이전트가) 뜨기 전에 주소를 흘려 한 번 터뜨렸다.
  - **B. 순서를 바꿔 DNS를 먼저 만든다.** 창이 2분 54초 → 약 10초. **줄일 뿐 없애지 못한다.**
    즉시 누르면 여전히 걸린다. 빌드 실패 시 이름만 남는 부작용도 생긴다.
  - **C. 고정 슬롯.** `preview-1`~`preview-5`를 한 번만 만들고 PR마다 배정. DNS를 영원히
    안 건드리므로 확실하다. 대가: 주소에 PR 번호가 안 들어가고, 슬롯 배정 로직이 는다.
  - **D. 와일드카드 자리표시(채택).** `*.sangjun.dev`를 **프록시된** CNAME으로 걸어
    모든 이름이 항상 주소를 받게 한다.

- **채택: D.** 핵심은 **"없음"(NXDOMAIN·NODATA, 30분 캐시)을 "아직 준비 안 됨"(HTTP 404,
  캐시 안 됨)으로 바꾸는 것**이다. 일찍 눌러도 새로고침이면 풀린다.
  정확히 일치하는 레코드가 와일드카드를 이기므로 기존 앱은 영향이 없고, 되돌리기는 레코드
  삭제 하나다.

  ```
  *.sangjun.dev  CNAME  arka.sangjun.dev  proxied=true  ttl=300
  ```

  실측(2026-09-11):

  | | 전 | 후 |
  |---|---|---|
  | 아직 없는 이름 | NXDOMAIN | **HTTP 404** |
  | `arka`·`storybook`·`file`·`label`·`battlesight`·`pr-19` | 302/200 | **그대로** |

- **함께 바로잡을 것 — 내가 두 번 틀렸다.**
  1. **"Free 요금제는 와일드카드를 프록시할 수 없다"**고 조사 단계부터 계속 말했고 계획
     문서(ADR 0006의 기각 항목 포함)에도 그렇게 적었다. **실제로는 된다**(API가 `proxied=true`를
     받았고 동작한다). 문서를 근거로 단정하고 시험하지 않은 탓이다.
     → **그 전제 위에 선 "PR마다 DNS 레코드를 만든다"는 판단을 다시 봐야 한다.**
  2. 처음에 **DNS-only**로 걸었더니 CNAME 체인이 `cfargotunnel.com`에서 끝나 **A 레코드가
     없는 NOERROR**가 됐다. NODATA도 SOA 최소 TTL로 캐시되므로 **고쳐지지 않았다.**
     프록시를 켜야 주소가 나온다.

- **강제할 수 있는가**: 부분적으로.
  - 이 레코드가 **왜 있는지**를 모르면 누가 지운다 → `docs/operations.md`와 ADR에 남긴다.
  - **존재 검사는 CI로 가능하다** — 배포 잡이 아무 이름이나 하나 조회해 NXDOMAIN이 아닌지 본다.
    (지금은 없다. 만들면 이 결정이 문장이 아니라 동작이 된다.)

- **남은 질문**: 프록시된 와일드카드가 되므로 **PR별 DNS 레코드가 여전히 필요한가.**
  없애면 `up`/`down`에서 DNS 호출이 통째로 사라지고 배포가 빨라진다. 다만 와일드카드 하나에
  전부 기대면 그 레코드가 단일 장애점이 되고, `down`이 이름을 회수하지 못해 닫힌 PR의 주소가
  계속 404를 준다(지금은 NXDOMAIN으로 사라진다). **별도 검토가 필요하다.**

- **상태**: 결정됨(D 적용, 실측 완료) → ADR 0006 개정 + `docs/operations.md` 반영 대기
