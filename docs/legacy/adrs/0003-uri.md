# ADR 0003: 문자열 경로 대신 URI를 쓴다

## 결정:
- 에디터는 단순히 파일만 여는 것이 아니라 git의 이전 버전도 열어보게 되는데, 디스크 파일과 git의 이전 버전은 단순 경로만으로는 구분할 수 없다.
- 이를 해결하기 위해서, `scheme`, `authority`, `path`를 갖는 URI를 쓴다 (`scheme://authority/path`).
- URI는 값 클래스로 두고, `URI.parse()`/`URI.file()`로만 생성해 검증을 우회할 수 없게 한다.
- 단, query/fragment 형태의 URI는 두지 않는다.
- `authority`는 이 파일이 어디에 속하는지를 가리킨다 — `git://HEAD/main.py`의 리비전, `run://abc123/out.log`의 실행. 디스크 파일처럼 속한 곳이 없으면 비고, 그때가 슬래시 세 개(`file:///a.txt`)다.
- `path`는 어느 스킴이든 workspace 루트 기준 상대경로이며 선행 슬래시를 갖지 않는다(`file:///a.txt` → `"a.txt"`). 클라이언트가 서버 PC의 실제 경로를 몰라도 되고, 데스크톱·모바일 어디서 열어도 같은 URI가 통한다.

## 기각:
- scheme 없는 경로(`/workspace/main.py`) — 현재 파일과 git 이전 버전이 같은 문자열이 되어 구분할 수 없다.
- 디스크 절대경로를 `path`로 쓰기 — 클라이언트가 서버의 파일시스템 구조를 알아야 하고, 기기가 바뀌면 같은 URI가 다른 것을 가리킨다.
- 검증된 문자열 타입(branded string) — JSON 전송과 `Map` 키는 편하지만, `as Uri`로 검증을 우회할 수 있고, 앞으로 필요해질 경로 조작(`basename`·`dirname`·`join`)을 붙일 자리가 없다.
- query/fragment는 당장 필요하지 않기에 없는 형태로 관리한다.
- `authority` 없이 리비전·실행 ID를 `path` 앞에 붙이기(`git:///HEAD/main.py`) — `path`가 스킴마다 다른 모양이 되어, 파일 경로로 쓰려면 매번 앞부분을 잘라내야 한다.
- 슬래시 두 개(`file://a.txt`) — `a.txt`가 authority로 해석되어 파일명이 컴퓨터 이름 자리에 들어간다.
- 슬래시 없음(`file:a.txt`) — `file:`은 표준 URL 파서가 `file:///a.txt`로 되돌리는 special scheme이라 `run:`·`git:`과 다르게 굴러간다.

## 상태:
승인됨.
